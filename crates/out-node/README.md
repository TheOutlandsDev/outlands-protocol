# OUT node orchestration

`out-node` is the storage-independent coordination layer between untrusted block bytes, pure consensus validation, and an implementation of `ConsensusStorage`.

This slice contains no TCP/UDP sockets, peer discovery, public RPC, wallet, autonomous mining service, CUDA backend, signal handling, installed daemon, service configuration, or host integration. Its P2P runtime remains transport-independent and owns only deterministic state machines and bounded in-memory queues. The optional Unix-only operator module binds one caller-selected local socket path and serves one authenticated command per explicit call; it does not create a background thread or alter networking configuration. A repository-local executable repeatedly drives that explicit boundary until authenticated shutdown. Consensus and mining time inputs remain caller supplied.

Only the frozen `Testnet` and `Devnet` profiles are constructible. There is deliberately no mainnet profile, fallback, numeric network selector, or provisional target. Adding mainnet requires the independently verified final descriptor and genesis artifacts described in `docs/open-decisions.md`.

## Processing boundary

Block processing has two explicit durable phases:

1. `validate_and_store` obtains parent state/history snapshots, performs complete pure consensus validation, and stores the resulting opaque validated commit as an inert branch block.
2. `activate_best_chain` asks the backend for the deterministic cumulative-work winner, enforces the local maximum-reorganization policy, and atomically applies the returned plan.

`process_block` composes both operations. If activation fails after storage succeeds, its error contains the stored block identity so callers do not retry under the false assumption that nothing was persisted. A policy pause is a successful, explicit outcome: the block remains stored while the selected chain remains unchanged.

Durable stores remain fail-closed during interrupted prepare/publish operations. For a `RecoverableConsensusStorage`, the node exposes the backend recovery status and exact rollback/finalization operation without inventing or repairing consensus state.

## Pinned bootstrap

`NodeBootstrap` supports only `Testnet` and `Devnet`. It decodes the exact independently verified 223-byte genesis header for the selected network, runs the pinned genesis header/PoW validator, compares the computed block ID and PoW hash with the frozen artifacts, recomputes the empty state root, checks the dedicated empty-genesis transaction root, and round-trips the complete canonical genesis block before constructing storage.

Factories create an in-memory node or create/open redb and RocksDB nodes. Persistent database paths are caller-supplied; the library does not select directories, inspect mounts, create services, or read environment configuration. Opening an existing database with the other network profile fails closed.

## Pure synchronization planning

`sync::SyncCoordinator` consumes only header batches already correlated by `out-p2p`. It validates every header through the existing consensus ancestry, timestamp, target, PoW, and cumulative-work rules using a bounded disposable read-through overlay. A failed batch commits no overlay or download-queue changes. Complete blocks remain the only objects admitted to `ConsensusStorage` through `Node`; `mark_block_stored` refuses to retire a header until authoritative storage exposes matching validated metadata.

Locator size, initial linear steps, maximum ancestry walk, overlay capacity, and per-request block count are explicit caller policy. Locators are generated from exact validated parent links, end at genesis when the walk policy permits, and never depend on database iteration order. Block retrieval work is emitted in validated chain order and individual block completion/retry remains explicit because P2P v0 has no `GET_OBJECTS` terminal marker.

`Node::deliver_scheduled_block` is the pure delivery bridge from a decoded session action to full block processing. It requires a nonzero request ID and an in-flight header ID before canonical re-encoding and complete `Node::process_block` validation. Peer-invalid bodies and temporarily unacceptable blocks are requeued; local read/validation failures are never attributed to the peer. Storage-mutation uncertainty remains in flight until recovery. After recovery, an already-stored block is reconciled and best-chain activation runs before sync state is retired, preventing both duplicate ingestion and skipped activation. Requested children arriving before their parents are treated as retryable local ordering failures.

## In-memory integration harness

`harness::InMemoryTwoNodeHarness` connects an outbound target session to an inbound source session without opening a socket. Every handshake, header request/response, object request, and full-block response is encoded into exact P2P v0 bytes, decoded for the receiving network, passed through that peer session, and recorded in a deterministic transcript. Header responses are selected only from validated canonical ancestry; downloaded blocks then pass through the existing sync coordinator, complete consensus validation, authoritative storage, and best-chain activation.

The source relay catalog is caller-supplied, bounded, verified against source canonical metadata, and explicitly non-authoritative. It avoids adding raw-block retrieval to the consensus-storage interface or relying on backend iteration order. All time and resource limits remain caller inputs. The harness is an integration and fault-injection boundary, not a transport implementation: it performs no peer discovery, asynchronous work, network I/O, sleeping, or wall-clock reads.

Adversarial coverage drives the same encoded-frame path for response timeouts, explicit request rejection, multiple bounded header batches, child-before-parent delivery, duplicate full blocks, cumulative-work fork reorganization, and replay after an interrupted authoritative store. Timeout and rejection return header synchronization to idle; out-of-order children remain retryable local failures; duplicates cannot re-enter validation after their schedule is retired; and post-recovery replay reconciles already-published storage before activation. A harness-only caller limit can reduce headers per response below the wire maximum to exercise multi-round behavior without changing protocol limits.

## Pure multi-peer coordination

`peers::MultiPeerCoordinator` records bounded decoded inventory, retains caller-prioritized object order, and chooses an eligible announcing peer by failure count, current in-flight count, then local peer ID. These are operational scheduling rules only: announcements are untrusted hints, local peer IDs never enter consensus, and the coordinator cannot select or validate a chain. Every capacity, request deadline, retry count, exponential-backoff bound, and request-ID origin is caller supplied. Expired assignments are returned in request-ID order and remain unchanged until the caller explicitly completes or retries them.

The orphan pool stores one canonical byte representation per block under global count, serialized-byte, per-peer, and per-parent limits. Same-ID conflicting bytes fail closed, peer removal is refused while that peer owns retained orphans, and children are released in ascending block-ID order only after the caller reports their parent available. Released bytes still require complete canonical decoding and consensus validation. Caller-selected monotonic expiry reclaims records deterministically by receipt tick and block ID.

`peers::BoundedMemoryTransport` is a FIFO fault and integration transport for exact frame bytes. Its frame count, total bytes, and individual frame length are independently bounded and checked before enqueue. It performs no decoding, sleeping, asynchronous work, socket creation, or host I/O; malformed and truncated frames may intentionally pass through it so the receiving codec can be tested.

## Three-node integration

`multi_harness::ThreeNodeHarness` joins one target and exactly two simulated remote nodes through independent outbound/inbound session pairs and the bounded memory transport. It performs real identity handshakes, correlated header requests, canonical header validation, inventory delivery, deterministic multi-peer object assignment, exact single-block sync reservation, full block responses, consensus validation, authoritative storage, and activation. The transcript retains every carried frame byte with its peer and direction.

Object-request correlation belongs to `MultiPeerCoordinator`, because P2P v0 session correlation tracks header and ping requests while `GET_OBJECTS` has no terminal batch marker. Both an exact wire `REJECT` and a caller-tick timeout therefore retry the same scheduled block through the coordinator without draining unrelated sync work. Tests prove failover from the first remote to the second and convergence to the identical validated tip.

When a requested child arrives before its parent, complete block validation classifies the missing parent as local and requeues the sync item. The harness retains the child's one canonical encoding in the bounded orphan pool and completes the network assignment. After the parent is validated, stored, and activated, the child is reserved exactly, re-encoded into another remote-to-target frame, passed through the target session, and fully validated again. Header-only and orphan data never become authoritative state.

## Deterministic runtime

`runtime::NodeRuntime` is a transport-independent event loop around a recoverable node and a bounded set of peer sessions. Startup enters `Running` only when authoritative storage is clean; an interrupted backend enters `Recovering`, rejects peer registration and input, and requires an explicit successful recovery operation before networking work is admitted.

Every peer, inbound-frame, inbound-byte, individual-frame, output, per-step input, and per-step peer-poll limit is explicit caller policy and validated at construction. Incoming frames are enqueued atomically and processed in FIFO order. Peer timeout polling uses ascending local peer ID, and output backpressure stops processing without dropping or reordering queued input. Exact P2P decoding happens only after bounded admission; malformed frames become explicit output events and cannot reach a session or panic the runtime.

The runtime accepts caller-supplied monotonic ticks and rejects clock regression. Shutdown transitions from `Running` to `Draining`, rejects new work, processes already admitted frames, and reaches `Stopped` only after both inbound and output queues are empty. It creates no threads, tasks, timers, sockets, files, or services; an eventual daemon or asynchronous transport must drive this state machine without changing its ordering and failure semantics.

## Transport-driver and lifecycle boundary

`driver::TransportDriver` is the narrow ownership boundary for a future socket implementation. It starts only after authoritative storage is clean, receives one complete bounded `(peer_id, frame_bytes)` value at a time, accepts one outbound frame at a time, and exposes explicit shutdown polling. A backpressured or failed send MUST return the exact unchanged frame to its caller. Driver allocation MUST be bounded before buffering attacker-controlled declared lengths, and driver failures are local failures rather than evidence that a block or transaction is consensus-invalid.

`driver::DaemonHarness` deterministically composes that contract with `NodeRuntime`. It uses caller-supplied step budgets, retains one input frame when the runtime is backpressured, preflights complete runtime-output batches before consuming them, separates typed local session events from encoded outbound P2P frames, and bounds both pending frame count and bytes. A frame that cannot be admitted for a non-capacity reason remains available for explicit caller quarantine; it is never silently discarded.

The lifecycle is `Created -> Recovering -> Running -> Draining -> Stopped`, with an explicit local `Failed` state. The driver is not started while storage requires recovery. Graceful shutdown stops new transport admission, drains work already accepted by the runtime, preserves FIFO output under transport backpressure, and waits for the driver to report its output side drained. `BoundedMemoryDriver` implements and fault-injects this interface using independent bounded in-memory queues; it is a test driver, not networking code.

## Application dispatcher

`dispatcher::ApplicationDispatcher` is the bounded application layer joining `DaemonHarness`, peer sessions, `MultiPeerCoordinator`, `SyncCoordinator`, and authoritative block delivery. Each caller-driven step has explicit event and command budgets. An established session registers an eligible peer; inventory is retained only as an untrusted source hint. Header synchronization selects the greatest advertised peer height with ascending local peer ID as the deterministic tie break, builds a locator from validated ancestry, correlates the exact header request, and validates every returned header through consensus before scheduling block objects.

Dispatcher commands pass through the typed `NodeRuntime` command boundary; callers never receive mutable peer sessions. Because protocol v0 has no multi-object terminal marker, each object request contains exactly one typed block or transaction inventory entry and uses one nonzero request ID. Exact rejects and timeouts requeue the same object through bounded retry and peer-failover policy. A returned block must match both its assigned peer and block ID before `Node::deliver_scheduled_block` can perform complete consensus validation and authoritative storage. A child received before its parent is retained as one bounded canonical orphan; after parent acceptance, descendants are replayed in ascending block-ID order through the full validation path. A returned transaction must match the requested transaction ID before the non-consensus mempool can validate it.

Consensus-invalid header batches and structurally or cryptographically invalid correlated transactions are reported to the session under the explicit protocol-violation score. Temporary timestamp failures, unavailable local ancestry, storage failures, driver faults, and capacity pressure remain local conditions. If durable storage starts dirty, dispatcher construction deliberately defers both `SyncCoordinator` and mempool construction and driver startup until explicit recovery reports clean storage. The dispatcher creates no sockets, threads, timers, files, wall-clock reads, or RPC services, and no dispatcher or mempool decision can alter consensus validity or chain selection.

Peer disconnect is an explicit cross-layer cleanup operation. The driver, runtime, daemon queues, and multi-peer scheduler remove only that peer's disposable state while retaining every other peer's FIFO order. In-flight blocks return to both the object scheduler and sync queue in request-ID order without a peer penalty, and the local peer ID becomes reusable only after cleanup completes. Canonical orphan bytes remain globally bounded and retain source attribution, but are detached from the departed peer's live quota; they still require the identical complete consensus replay path after their parent becomes authoritative.

Dispatcher restart state is reconstructed exclusively from authoritative consensus storage. A newly constructed dispatcher reads and validates the persisted canonical tip, creates empty peer/header/request/orphan state, and never attempts to serialize or restore transient network hints. Tests close and reopen redb around an activated block and prove the reconstructed sync tip matches storage while prior sessions disappear. A dirty durable store still follows the recovery gate before sync construction or driver startup.

## Bounded non-consensus mempool

`mempool::Mempool` is a disposable, deterministic holding policy for regular transactions. It accepts only a complete canonical regular envelope, derives the exact consensus transaction ID, applies the frozen network identity, active version, minimum fee, strict Ed25519 verification, nonce, balance, and checked monetary transition routines, and mutates its overlay only after validation succeeds. Reward transactions are never admitted. Count, total encoded bytes, per-sender count, template count, and template bytes are independent nonzero caller limits; capacity failures are local policy outcomes and do not penalize peers.

Admission order is FIFO and is also the state-dependency order. Each accepted transaction is evaluated against the authoritative canonical snapshot plus prior accepted changes, so sequential nonces from one sender are deterministic. Template selection takes the longest FIFO prefix fitting both template limits; it does not sort by fee, hash-map order, arrival thread, or database order. The pool stores canonical transaction bytes for exact accounting and uses ordered maps only for lookup and working-account overlays.

Before admission and on every dispatcher step, a changed canonical tip causes an atomic rebuild from fresh branch-anchored state and confirmed-transaction snapshots. Previously accepted transactions are replayed in their original FIFO order; newly confirmed entries and entries no longer valid on the selected branch are removed deterministically. The current storage interface does not expose orphaned regular transaction bodies, so a reorganization does not automatically reinsert them. Wallets or peers MAY resubmit those bytes as ordinary non-consensus policy.

The mempool is deliberately not persisted. Restart, loss, or corruption of this cache cannot change balances, nonces, roots, block acceptance, cumulative work, or chain selection. A fresh dispatcher reconstructs an empty pool from authoritative storage, and storage recovery must finish before a pool exists.

## Candidate construction and CPU reference PoW

`mining::build_candidate` constructs a testnet/devnet work candidate from one exact canonical tip and the reconciled mempool. Timestamp and local Unix time are explicit caller inputs; the builder never samples a clock. Height, median-time acceptance, epoch target, delayed-testnet exception, and fixed-devnet behavior are derived through the same validated-ancestry routine used by complete header validation. A tip change observed during construction fails the build rather than mixing snapshots.

The builder selects the FIFO mempool prefix that fits both local template policy and the exact consensus transaction-count/body-byte limits. It replays every selected regular transaction through canonical encoding, network/version checks, strict Ed25519 verification, ancestor replay protection, nonce/balance rules, and checked state transitions. It then constructs the sole reward transaction from the frozen subsidy plus exact accumulated fees, credits it last, recomputes issued supply, state root, transaction IDs, indexed Merkle root, and the canonical block envelope. Parent snapshot anchors, balances, supply, and state root are verified before use. The dispatcher exposes this operation without granting the candidate authoritative status.

`mining::mine_cpu` is the auditable CPU reference loop. It scans ascending `u64` nonces from a caller-selected start, performs no more than a nonzero caller-supplied attempt budget, hashes the exact canonical 223-byte header with the consensus PoW domain, and compares the unsigned big-endian digest to the full 256-bit target. It returns either the solved block and exact block ID/PoW hash/attempt count, the next nonce after budget exhaustion, or explicit nonce-space exhaustion. It creates no worker threads, tasks, timers, files, sockets, device contexts, or sleeps.

Candidate construction and PoW discovery are non-authoritative. Even a reported solution MUST enter the ordinary complete block-validation path before storage and best-chain activation. Tests build a candidate containing the independently verified regular transaction, prove byte determinism, find a bounded devnet CPU solution twice with identical results, process its exact bytes through full consensus, and reconcile the now-confirmed mempool entry. CUDA remains absent and any future implementation must reproduce this CPU result bit-for-bit.

`mining::MiningCoordinator` owns at most one transient job. Its nonzero attempt budget is fixed by caller policy at dispatcher construction; each explicit step performs no more work than that budget and records the exact next nonce plus checked `u128` total-attempt accounting. Starting a job replaces the previous transient job explicitly, cancellation returns its final snapshot, and restart reconstructs no job. A found solution is retained without rehashing until the dispatcher either submits or cancels it.

`ApplicationDispatcher::control_mining` is the typed local command boundary for operators and adapters. `Inspect` returns the frozen network profile, authoritative canonical tip, current mempool revision, and optional transient job snapshot without mutation. `Start` refuses to replace an existing job. `Refresh` requires an existing job, builds the replacement candidate first, and leaves the old job byte-for-byte intact if candidate construction fails. Both commands require an explicit first nonce. `Step` invokes exactly one bounded `mine_step`; it does not loop, sleep, sample a clock, or hide retry work. `Cancel` is idempotent and returns the removed snapshot when one existed. The command types remain independent of any transport or serialization.

## Authenticated Unix operator boundary

On Unix targets, `operator::UnixMiningControlServer` provides the first real local IPC adapter. It binds only a caller-selected Unix-domain socket path, refuses to unlink a pre-existing path, sets the socket mode to `0600`, accepts one connection and one command per explicit `serve_once`, applies caller-bounded read/write timeouts, and removes its socket on drop only when the path is still the exact socket inode it created. It creates no worker thread, accept loop, TCP/UDP port, service unit, secret file, or configuration file.

Every request and response uses the bounded binary format in `OPERATOR-PROTOCOL.md`. Frames are at most 16,512 bytes and declare a `u16` length before allocation; the ceiling admits a maximum 16,384-byte consensus transaction plus the operational envelope. A caller-provided 32-byte nonzero secret authenticates requests and responses with BLAKE3 keyed mode under distinct operational domains. Tags are compared in constant time. Nonzero `u64` request sequences must increase strictly within one server lifetime; authentication succeeds before replay state can change, and replayed commands never execute. The key is redacted from `Debug` and overwritten on drop. Key provisioning is deliberately outside the library: operators MUST generate it with a cryptographically secure random generator, transfer it through an already trusted local channel, and rotate it whenever the server restarts because replay state is transient.

The wire adapter exposes mining inspection/control, authoritative canonical account inspection, canonical signed regular-transaction submission, and graceful process shutdown. Account results are anchored to the returned canonical tip and exclude pending mempool effects. Transaction submission accepts bytes only—never private keys—and applies the exact canonical decoder, frozen network identity, strict signature checks, replay protection, nonce/balance validation, and bounded disposable mempool policy. Dispatcher failures are reduced to bounded operational status codes so storage internals are not disclosed over IPC. The socket protocol and mempool are non-consensus: loss, corruption, authentication failure, replay rejection, capacity pressure, or unavailability cannot change block validity, state roots, work, chain ordering, or durable storage semantics.

## Repository-local executables

The `out-node-local` binary is a testnet/devnet-only persistent node entrypoint. It explicitly selects create versus open, redb versus RocksDB, network, database path, operator socket path, and an optional local reorganization limit. It reconstructs the frozen genesis profile, opens or creates authoritative storage, completes any required durable recovery before binding IPC, starts the bounded application lifecycle, isolates malformed and wrongly authenticated connections, and drains cleanly only after an authenticated shutdown command. This entrypoint deliberately uses the bounded memory P2P driver: it provides persistent consensus processing and local mining control but does not connect to remote peers.

The `out-operator` binary is the matching authenticated client. Both binaries read one canonical 64-character lowercase key from standard input so the key is not placed in command-line arguments. They do not generate, save, search for, or log the key. Example shapes, with `OUT_OPERATOR_KEY_HEX` already populated through a trusted secret channel:

```text
printf '%s\n' "$OUT_OPERATOR_KEY_HEX" | cargo run -p out-node --bin out-node-local -- create redb devnet /chosen/path/out.redb /chosen/path/out.sock
printf '%s\n' "$OUT_OPERATOR_KEY_HEX" | cargo run -p out-node --bin out-operator -- /chosen/path/out.sock 1 inspect
printf '%s\n' "$OUT_OPERATOR_KEY_HEX" | cargo run -p out-node --bin out-operator -- /chosen/path/out.sock 2 account 00<64-lowercase-public-key-hex-characters>
printf '%s\n' "$OUT_OPERATOR_KEY_HEX" | cargo run -p out-node --bin out-operator -- /chosen/path/out.sock 3 submit-tx <canonical-signed-transaction-hex>
printf '%s\n' "$OUT_OPERATOR_KEY_HEX" | cargo run -p out-node --bin out-operator -- /chosen/path/out.sock 4 shutdown
```

Client sequence values MUST increase for the complete server lifetime. `account` requires the canonical lowercase 66-character binary-recipient hex. `submit-tx` requires lowercase hex of the complete canonical signed transaction and rejects input above the consensus transaction limit before hex decoding. `start` and `refresh` additionally require timestamp, local time, the binary-recipient hex, reward-extra hex (or `-` for empty), and first nonce. Integers use minimal decimal text with no leading zeroes. `--help` prints the exact positional syntax. Restart requires a freshly generated key and resets the sequence to a new lifetime.

The repository-local `out-wallet` companion can derive testnet/devnet Bech32m addresses and produce the complete canonical signed hex accepted by `submit-tx`. It runs offline, reads its Ed25519 seed from standard input, and never sends the seed through this operator protocol. Its exact workflow and limitations are documented in `../out-wallet/README.md`.

The executables are ordinary Cargo targets only. This project does not install them, create users or directories, choose production paths, modify permissions outside the caller-selected socket, create secret files, register services, configure systemd, or open TCP/UDP ports.

Every candidate records both its exact parent `ChainTip` and mempool revision. Admission of a new regular transaction or any canonical-tip reconciliation increments the revision with checked arithmetic. Before each work step, the coordinator compares both values with current state; a mismatch cancels the job as stale before performing more PoW. This is local mining policy only and cannot affect block validity.

`ApplicationDispatcher::mine_step` is the local acceptance bridge. It reconciles the mempool, advances the coordinator once, and preflights enough bounded announcement capacity for every currently established peer before submitting a retained solution. Backpressure leaves the solution pending and performs no duplicate hashing or partial block application. Submission re-encodes the solved block and calls the ordinary `Node::process_block` path, so complete header, PoW, transaction, state, storage, and best-chain rules remain authoritative.

After successful canonical activation, the dispatcher admits the exact validated block to the ordinary bounded relay cache, reconciles confirmed mempool entries, and queues one typed request-ID-zero block inventory announcement for each established peer in ascending local peer-ID order. A block stored but not selected—such as a local reorganization-policy pause—is reported and is not announced as canonical. A local processing failure returns the exact partial-progress error and cancels the job to avoid blindly duplicating a possibly durable mutation. Integration coverage proves the complete job-to-validation-to-storage-to-relay-to-wire-announcement path without sockets or simulated responses.

## Bounded inbound serving

`serving::InboundServing` handles established-peer `GET_HEADERS` and `GET_OBJECTS` requests without expanding the consensus-storage interface. Pending requests, responses per dispatcher step, headers per response, ancestry records, relay blocks, and relay bytes are independent nonzero caller limits; the header count cannot exceed the wire maximum, and response work cannot exceed the dispatcher command budget. Requests remain in a bounded FIFO until the typed runtime response command has capacity, so transport or runtime backpressure cannot silently lose or reorder them. Disconnect removes that peer's queued service requests explicitly.

Header responses start at the authoritative canonical tip and follow exact validated parent links backward. The first locator entry found on that ancestry is the common point; returned headers are ascending, stop at the requested block when encountered, and never exceed the configured response bound. Missing common ancestry produces a correlated operational reject. Database iteration order, disposable sync overlays, advertised peer tips, and the relay cache cannot influence the selected headers.

Full blocks are served only from a separately bounded FIFO relay cache populated after this dispatcher completes full block validation. The cache is non-authoritative, is empty after restart, and is never a source for balances, roots, work, or chain selection. Every lookup rechecks the cached header against the current canonical ancestry, so stale fork entries are refused after a reorganization. Protocol v0 has no multi-object terminal marker; this node therefore requires exactly one typed entry per `GET_OBJECTS` request. A single block entry is served only from the canonical relay cache; a single transaction entry is served only while present in the reconciled mempool. Empty, multi-entry, missing, stale, and uncached requests receive a correlated reject with the exact request ID. Relay or mempool loss merely reduces serving availability and cannot alter consensus.

Outbound block and transaction inventory uses a typed request-ID-zero session command. Pending announcements, announcements per dispatcher step, and entries per announcement are independently bounded, with the entry limit capped by the P2P wire maximum. A complete block announcement is checked atomically against one canonical-ancestry snapshot and the relay cache; a complete transaction announcement is checked atomically against the current mempool. Empty, duplicate, uncached, stale-fork, oversized, and pre-handshake announcements are rejected without partial queue mutation. Disconnect explicitly discards that peer's queued announcements.

## Two-dispatcher duplex integration

`duplex_harness::TwoDispatcherDuplexHarness` owns two complete `ApplicationDispatcher<InMemoryConsensusStore, BoundedMemoryDriver>` applications. It performs the real handshake and moves only exact encoded frames from each driver's outbound FIFO to the other driver's inbound FIFO. Direction order is deterministic—left to right, then right to left—and each direction has a strict per-round frame budget. No request or response is simulated outside the applications.

The left relay is seeded only with blocks independently verified as already stored on its exact canonical ancestry. The left dispatcher then emits a bounded inventory notification; the right dispatcher obtains headers and full blocks through the left dispatcher's ordinary inbound-serving queue. A separate funded-node test submits the independently verified regular transaction vector, announces its ID, observes the remote's correlated `GET_OBJECTS`, transfers the exact `TX` response, and proves admission of the identical transaction on the right. Tests also prove identical-tip convergence, byte-stable transcripts, convergence under one-frame directional backpressure, longer-fork reorganization, refusal of backward header sync toward a strictly lower peer, and atomic rejection of missing, duplicate, and stale relay announcements. The harness creates no sockets, tasks, threads, sleeps, wall-clock reads, files, or services.

Persistent duplex fault tests run the same exact-frame path with redb and RocksDB targets. They disconnect after partial synchronization, purge peer-owned queued frames, reconnect with reusable local peer IDs, reannounce the bounded relay inventory, and converge without losing validated progress. Separate prepare- and publish-interruption cases crash during synchronized block storage, reopen the backend directly, require the exact `RolledBackPrepared` or `FinalizedPublished` recovery result, reconstruct fresh applications, and compare the final canonical tip plus complete parent-state snapshot with the in-memory source.

Normal node construction remains fail-closed while a persistent recovery marker is dirty. Recovery therefore occurs at the backend boundary before reconstructing a clean node application. If publication completed before activation was interrupted, header synchronization deliberately reschedules that stored-but-inert block body. `Node::deliver_scheduled_block` then verifies matching authoritative metadata, avoids duplicate ingestion, runs deterministic best-chain activation, and retires the sync entry only after reconciliation succeeds.
